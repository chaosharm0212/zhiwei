线上监控的 LCP p75 是 4.2 秒。这个数字维持了半年，每周的报表上都写着「待优化」，然后被下一件事盖过去。

这次终于做了。过程比想象的简单，也比想象的更依赖测量。

## 先别急着改

性能优化最常见的错误，是照着清单改：加 preload、开 gzip、懒加载图片……改了一堆，LCP 只掉了 200ms，因为你并不知道瓶颈在哪。

我做的第一件事是把 LCP 拆开。找一个真实用户的录屏，把首屏拆成三段：

- **T0 到首字节**：DNS、TLS、服务端渲染时间；
- **首字节到文字出现**：HTML 解析、CSS 阻塞、字体阻塞；
- **文字出现到主图绘制**：图片请求与主线程调度。

拆开之后就清楚了：问题不在服务端（首字节 180ms，很好），也不在图片（图片在 CDN 上，缓存命中），而在第二段。

## 四个发现

| 阶段 | LCP (p75) | 主要瓶颈 |
| --- | --- | --- |
| 优化前 | 4.2s | 字体阻塞 + 首图未设尺寸 |
| 去掉阻塞字体 | 3.4s | 长任务挤压主线程 |
| 首图预加载并设定尺寸 | 2.2s | 第三方脚本 |
| 延迟第三方脚本 | 1.1s | 无 |

### 一、字体在阻塞渲染

我们用了自定义中文字体，在 CSS 里写了 `@font-face`，但没有设置 `font-display`。浏览器会等字体，最多等三秒。

改法很简单：`font-display: swap`，同时用 `size-adjust` 让回退字体的度量接近目标字体，减少切换时的跳动。

```css
@font-face {
  font-family: "TextSerif";
  src: url("/fonts/text-serif.woff2") format("woff2");
  font-display: swap;
  size-adjust: 96%;
}
```

这一项省了 800ms。

### 二、首图没有尺寸

看似低级，但我们确实漏了：图片只写了宽度 100%，没有 `width` / `height` 属性。图片加载完成后布局重排，LCP 的计时被打断。

补上明确的比例和 `fetchpriority="high"` 之后，浏览器能在发现它的第一时间开始下载。

### 三、主线程上的长任务

这是最难的一项。打开 Performance 面板，主线程上有三个超过 300ms 的任务，全部来自一个「通用」组件库的初始化——它做了大量与首屏无关的注册。

处理方式是把它拆成两份：首屏需要的，和首屏之后才需要的。后者用 `requestIdleCallback` 加载。

### 四、第三方脚本

埋点、客服、A/B 实验，加起来 480KB，全都在文档头部同步加载。

改成 `defer`，并把 A/B 实验的分组判定挪到服务端。这一项直接砍掉了 1.1 秒。

## 一条经验

> 只要你在猜，就一定会优化错地方。先让数据说话。

这次优化没有用到任何技巧性的方案：没有预渲染，没有流式 SSR，没有边缘计算。只是一次次测量，然后改掉真正的瓶颈。

有时候性能问题不是技术问题，而是**没人愿意花两个小时盯着火焰图**。
